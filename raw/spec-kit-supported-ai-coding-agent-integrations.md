<h2 id="list-available-integrations">List Available Integrations</h2>
<pre><code class="lang-bash">specify integration list
</code></pre>
<p>Shows all available integrations, which one is currently installed, and whether each requires a CLI tool or is IDE-based.
When multiple integrations are installed, the list marks the default integration separately from the other installed integrations.
The list also shows whether each built-in integration is declared multi-install safe.</p>
<h2 id="install-an-integration">Install an Integration</h2>
<pre><code class="lang-bash">specify integration install &lt;key&gt;
</code></pre>
<table>
<thead>
<tr>
<th>Option</th>
<th>Description</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>--script sh\|ps</code></td>
<td>Script type: <code>sh</code> (bash/zsh) or <code>ps</code> (PowerShell)</td>
</tr>
<tr>
<td><code>--force</code></td>
<td>Opt in to installing alongside integrations that are not declared multi-install safe</td>
</tr>
<tr>
<td><code>--integration-options</code></td>
<td>Integration-specific options (e.g. <code>--integration-options=&quot;--commands-dir .myagent/cmds&quot;</code>)</td>
</tr>
</tbody>
</table>
<p>Installs the specified integration into the current project. If another integration is already installed, the command only proceeds automatically when all involved integrations are declared multi-install safe. Otherwise, use <code>switch</code> to replace the default integration or pass <code>--force</code> to explicitly opt in to multi-install. If the installation fails partway through, it automatically rolls back to a clean state.</p>
<p>Installing an additional integration does not change the default integration. Use <code>specify integration use &lt;key&gt;</code> to change the default.</p>
<blockquote>
<p><strong>Note:</strong> All integration management commands require a project already initialized with <code>specify init</code>. To start a new project with a specific agent, use <code>specify init &lt;project&gt; --integration &lt;key&gt;</code> instead.</p>
</blockquote>
<p><strong>Version note:</strong> Controlled multi-install support was introduced in Spec Kit 0.8.5. If <code>specify integration install &lt;key&gt;</code> says another integration is already installed and only suggests <code>switch</code> or <code>uninstall</code>, check your local CLI with <code>specify version</code> and upgrade it. Running a one-shot command such as <code>uvx --from git+https://github.com/github/spec-kit.git specify ...</code> uses a temporary copy for that command only; it does not update the persistent <code>specify</code> executable on your <code>PATH</code>.</p>
<h2 id="uninstall-an-integration">Uninstall an Integration</h2>
<pre><code class="lang-bash">specify integration uninstall [&lt;key&gt;]
</code></pre>
<table>
<thead>
<tr>
<th>Option</th>
<th>Description</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>--force</code></td>
<td>Remove files even if they have been modified</td>
</tr>

<p>Uninstalls the current integration (or the specified one). Spec Kit tracks every file created during install along with a SHA-256 hash of the original content:</p>
<ul>
<li><strong>Unmodified files</strong> are removed automatically.</li>
<li><strong>Modified files</strong> (where you've made manual edits) are preserved so your customizations are not lost.</li>
<li>Use <code>--force</code> to remove all integration files regardless of modifications.</li>
</ul>
<h2 id="switch-to-a-different-integration">Switch to a Different Integration</h2>
<pre><code class="lang-bash">specify integration switch &lt;key&gt;
</code></pre>
<table>
<thead>
<tr>
<th>Option</th>
<th>Description</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>--script sh\|ps</code></td>
<td>Script type: <code>sh</code> (bash/zsh) or <code>ps</code> (PowerShell)</td>
</tr>
<tr>
<td><code>--force</code></td>
<td>Force removal of modified files during uninstall; when the target is already installed, overwrite managed shared templates while changing the default</td>
</tr>
<tr>
<td><code>--integration-options</code></td>
<td>Options for the target integration when it is not already installed</td>
</tr>
</tbody>

<p>If the target integration is not already installed, equivalent to running <code>uninstall</code> followed by <code>install</code> in a single step. In this mode, <code>--force</code> controls whether modified files from the removed integration are deleted. If the target integration is already installed, <code>switch</code> only changes the default integration, like <code>use</code>; in this mode, <code>--force</code> controls whether managed shared templates are overwritten while the default changes. <code>--integration-options</code> is rejected for already-installed targets because changing integration options requires reinstalling managed files; run <code>upgrade &lt;key&gt; --integration-options ...</code> first, then <code>use &lt;key&gt;</code>.</p>

<h2 id="faq">FAQ</h2>
<h3 id="can-i-install-multiple-integrations-in-the-same-project">Can I install multiple integrations in the same project?</h3>
<p>Yes, but it is intended for team portability rather than the default workflow. Multiple integrations are allowed automatically only when the installed integration and the new integration are declared multi-install safe by Spec Kit. For other combinations, pass <code>--force</code> to acknowledge that multiple agents may see unrelated agent-specific instructions or commands.</p>
<p>Spec Kit tracks one default integration in <code>.specify/integration.json</code> with <code>default_integration</code>, all installed integrations with <code>installed_integrations</code>, per-integration runtime settings with <code>integration_settings</code>, and a dedicated <code>integration_state_schema</code> for future state migrations. The legacy <code>integration</code> field remains as an alias for the default integration.</p>
<h3 id="which-integrations-are-multi-install-safe">Which integrations are multi-install safe?</h3>
<p>An integration is multi-install safe when it uses isolated agent directories, a dedicated context file that does not collide with another safe integration, stable command invocation settings, and a separate install manifest. Shared Spec Kit templates remain aligned to the single default integration.</p>

<h3 id="what-happens-to-my-changes-when-i-uninstall-or-switch">What happens to my changes when I uninstall or switch?</h3>
<p>Files you've modified are preserved automatically. Only unmodified files (matching their original SHA-256 hash) are removed. Use <code>--force</code> to override this.</p>
<h3 id="how-do-i-know-which-key-to-use">How do I know which key to use?</h3>
<p>Run <code>specify integration list</code> to see all available integrations with their keys, or check the <a href="#supported-ai-coding-agents">Supported AI Coding Agents</a> table above.</p>
<h3 id="do-i-need-the-ai-coding-agent-installed-to-use-an-integration">Do I need the AI coding agent installed to use an integration?</h3>
<p>CLI-based integrations (like Claude Code, Gemini CLI) require the tool to be installed. IDE-based integrations (like Windsurf, Cursor) work through the IDE itself. Some agents like GitHub Copilot support both IDE and CLI usage. <code>specify integration list</code> shows which type each integration is.</p>
<h3 id="when-should-i-use-upgrade-vs-switch">When should I use <code>upgrade</code> vs <code>switch</code>?</h3>
<p>Use <code>upgrade</code> when you've upgraded Spec Kit and want to refresh an installed integration's managed files. Use <code>switch</code> when you want to replace the current default with another integration; if the target is already installed, <code>switch</code> behaves like <code>use</code>.</p>
